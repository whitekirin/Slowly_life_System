# 制度檔維護協議

> 管轄範圍：`CLAUDE.md`、`.claude/docs/*.md`、`.claude/agents/*.md`。
> 動這些檔案之前必讀本檔。這套制度的最大風險不是被違反，而是被善意的小修改慢慢改壞（退化模式見 letter.md）。

## 1. 權限分級

**可以自行改（不必問使用者）**：
- 在任何制度檔的「教訓記錄」段**追加**一行（格式見 §3）。
- 修正已驗證失實的事實描述：路徑改了、指令變了、測試基線變了、bug 修掉了。**條件：先實際驗證新事實**（跑過指令、讀過檔案），改動時保留舊值註記（例：`基線 6 failed → 2026-08-01 起 4 failed`）。
- 修 typo、修壞掉的檔案連結。

**改之前必須先問使用者**：
- 修改或刪除任何**規則本體**（硬規則、升降級路徑、rubric 判準、權限分級本身）。
- 新增制度檔或重組檔案結構。
- 修改 `.claude/agents/*.md` 的 frontmatter（model、effort、tools）。
- 任何「放寬」方向的改動（把「必須」改成「建議」、提高重試上限等）。

**永遠不准做**：
- 刪除「教訓記錄」裡的條目（精簡要走 §4 流程）。
- 因為「這條規則這次不方便」而改規則。規則不方便 → 這次照做或問使用者，並把摩擦記進教訓記錄，累積夠了再議。

## 2. 修改流程（四步，不可跳）

1. **備份**：`cd D:/System_Of_Speeching && cp {目標檔} .backup/{檔名}.$(date +%Y%m%d).bak`
2. **改**：最小改動。一次只改一件事。
3. **read-back**：重讀改動段落，檢查所有引用的路徑、指令、工具名真實存在。
4. **對抗審查**（只有動了規則本體時需要）：派 fresh `verifier`，驗收條件為「(a) 全部制度檔之間無互相矛盾的指示 (b) 無失效的路徑/指令/工具名 (c) 無 Sonnet 等級會誤讀的模糊語句」。修到過為止。

## 3. 教訓怎麼寫

**寫到哪**：跟哪個主題最相關就寫進那個檔案末尾的「教訓記錄」段（診斷類 → 00-diagnosis.md；派工類 → model-dispatch.md；判斷類 → judgment.md；repo 事實類 → architecture.md）。跨專案通用的教訓，另外存一份到記憶系統（memory 目錄，見系統提示）。

**格式**（一行一條，強制）：

```
- [YYYY-MM-DD] {觸發情境，一句話} → {規則，一句話，可執行}
```

正例：`- [2026-07-05] Glob 裸搜 README.md 命中 376 個 node_modules 檔案 → 所有搜尋鎖定 path 參數到 backend/ 或 frontend/src/`
反例：`- [2026-07-05] 今天搜尋遇到一些問題，以後要更小心` ——沒有情境、沒有可執行規則，等於沒寫。

**什麼值得寫**：花了你超過 3 輪工具呼叫才發現的坑、使用者糾正過你的事、驗證後推翻的既有文件描述。
**什麼不值得寫**：只在這次任務成立的細節、repo 的 git history 已經記錄的事。

## 4. 精簡門檻與流程

觸發條件（任一）：某檔的教訓記錄超過 15 條；某制度檔超過 300 行；CLAUDE.md 超過 150 行。

流程：向使用者提議精簡 → 獲准後備份 → 合併重複條目、把已多次驗證的教訓「晉升」成規則本體、把過時條目移到 `.backup/` 的歸檔檔 → 走 §2 第 4 步對抗審查。**精簡是合併與晉升，不是刪除資訊。**

## 5. 制度與現實衝突時

發現制度檔的描述和 repo 現實不符（規則引用的檔案不存在了、指令跑不動了）：
1. 以現實為準，別為了服從文件而扭曲操作。
2. 當下驗證現實後，按 §1 的「事實描述」權限立即修正文件。
3. 若不符的是**規則本體**賴以成立的前提（例如某個 agent 類型從環境中消失），停下來問使用者，附上你建議的修法。
