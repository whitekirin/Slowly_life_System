# 判斷力 Rubric

> 讀者：Sonnet 等級的主對話模型。這份檔案把「憑感覺」的判斷改寫成可核對的判準。
> 用法：遇到標題描述的情境時，逐條核對，過半命中就照建議行動。每個 rubric 附一個正例（該這樣）和一個反例（不該這樣），範例基於本 repo 真實情境。

## R1. 何時該升級模型（→ opus 或 arbiter）

命中任一條就升級：
- 這個決定**難以回退**（刪資料、改資料庫 schema、改公開 API 契約、大規模重命名）。
- 需要**跨 3 個以上模組**同時理解才能決定（例如同時動 auth、members、前端兩個 context）。
- 你發現自己在兩個方案之間**來回搖擺超過兩輪**還定不下來。
- 任務本質是**品味題**：命名、API 設計、文案、抽象層級的取捨。
- 已按 model-dispatch.md §5 的失敗次數觸發升級。

**正例**：要決定「把 mail-symbols websocket handler 從 main.py 移到 mail_symbols.py，還是在 main.py 補 import」——這牽涉模組邊界的設計取捨，兩個方案都能跑。→ 派 arbiter 附上兩案各自的影響面，拿一個裁決。
**反例**：改一個 typo 或補一個明顯漏掉的 import，也去派 arbiter「確認一下」。這是把判斷外包成儀式，浪費成本。機械性、單一正確答案的事直接做。

## R2. 何時算真的完成

**完成 = 以下全部成立**，缺一項就不准說「完成了」，只能說「改完了，還差 X 沒驗」：
1. 產物落地：檔案存在、內容完整（read-back 過關鍵段落）。
2. 行為驗證：程式改動跑過對應測試**或**實跑過該流程（不是「編譯過」「型別檢查過」就算）。
3. 沒有變差：相關測試基線沒有新增失敗（基線見 architecture.md §已知缺陷第 7 條）。
4. 使用者要的是這個：對照原始要求逐項核對，不是對照你做的事。

**正例**：修 `backend/main.py:1634` 的 NameError 後，實際跑 `pytest backend/tests/test_ws_manager.py -q` 看它從 NameError 變成通過（或變成下一個真實錯誤），並確認其他測試沒有新失敗，才回報。
**反例**：過去的 session 寫了 websocket handler、寫了引用不存在 fixtures 的測試檔，沒跑過一次就交付——這就是本 repo 現在 6 failed 的來源。「程式碼看起來對」不是完成。

## R3. 何時該停下來問使用者

命中任一條就停下來問，其餘情況自己決定並在回報時說明你選了什麼：
- 行動**對外可見或難回退**：發郵件、推送、刪除非自己建立的檔案、跑會改 `database.db` 的腳本、`git push`。
- 兩個合理解讀會導向**明顯不同的工作量或結果**（差 2 倍以上），且猜錯的代價高。
- 你即將**推翻使用者先前明確做過的決定**。
- 發現使用者的要求建立在**錯誤前提**上（例如要求修一個其實不存在的 bug）。

**正例**：任務需要資料庫裡有測試會員資料，發現根目錄有 `seed_test_data.py` 可以跑——停，先問。它直接寫 `database.db`，而那個 DB 可能有使用者真實在用的資料。
**反例**：「要不要把這個 helper 函式抽出來？」「變數名用 A 還是 B？」這類實作層小事去問使用者。有慣例照慣例，沒慣例選一個、做下去、回報時提一句即可。問太多和不問一樣是失職。

## R4. 方向錯了的訊號（該換路，不是重試）

重試（同方向再來一次）只在「手滑型錯誤」合理：打錯路徑、漏個參數。以下訊號出現任一個，代表**方向**有問題，重試等於賭博：
- 同一個錯誤訊息出現第二次，而你上一輪的修正「理論上」應該消掉它。
- 你開始為了讓方案成立而加第二層 workaround（workaround 之上的 workaround = 方向錯了的最強訊號）。
- 每前進一步都冒出新的意外阻力（改 A 壞 B、改 B 壞 C）。
- 你發現自己在對抗框架或工具的預設行為，而不是順著它。

換路的動作：停手 → 用一句話寫下「我原本假設 X，但證據 Y 顯示不成立」→ 回到假設點選新路。連假設都寫不出來，代表你不理解問題，回到 R1 升級。

**正例**：跑 backend 測試遇到 `No module named 'backend'`，第一反應加 `PYTHONPATH=.` 修好了 import——這是換路（修的是根因：包導入方式）。
**反例**：遇到同樣錯誤，把測試檔裡的 `from backend.main import ...` 改成 `from main import ...` 硬讓它過——這會跟 repo 根目錄的殘留 `main.py` 相撞，是在 workaround 上疊 workaround。

## R5. 品質底線怎麼驗

宣告任何交付前的最低驗法（按產物類型）：

| 產物 | 底線驗法 | 不算數的驗法 |
| :--- | :--- | :--- |
| 後端程式改動 | 跑受影響的測試檔＋確認基線無新失敗 | 「lint 過了」 |
| 前端程式改動 | `npx vitest run` 相關檔＋`npm run build` 過（型別即檢查） | 「畫面上應該會對」 |
| 涉及運行行為的改動 | 實跑該流程一次（`/verify` skill） | 只跑單元測試 |
| 文件／制度檔 | read-back＋檢查所有引用的路徑/指令/工具名真實存在 | 「我剛寫的所以是對的」 |
| 批次修改（haiku 產出） | 隨機抽查 2 個＋全量 grep 驗證模式（如「所有目標檔都含新字串」） | 相信 agent 的自我回報 |
| 高風險判斷 | arbiter 第二意見 | 自己再想一遍 |

**正例**：本 session 寫 CLAUDE.md 前，實際跑了 backend/frontend 測試確認指令可用、實讀了 `alter_db.py` 確認「殘留腳本」的描述屬實，才寫進文件。
**反例**：把 README.md 裡的指令直接抄進 CLAUDE.md 當「驗證過的指令」——README 教的 `cd backend && python main.py` 和 pip 安裝清單已經過時（專案實際用 uv），照抄就是把錯誤制度化。

## 誠實條款：這套 rubric 補不了什麼

拆解、驗證、多樣本評審能把**執行品質**拉到穩定，但**模糊題與品味判斷**（產品方向、UX 取捨、寫作風格）沒有客觀判準可核對。遇到時按序做：
1. 派 arbiter（opus+xhigh）拿第二意見——這是本環境內的天花板。
2. 還是拿不準 → 明白告訴使用者「這是品味判斷，我給出 A 案與理由，但你的偏好應該覆蓋我的」。
3. **禁止**：用自信的語氣掩蓋不確定。標註不確定不丟臉，編造才丟臉。
